This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Structure

Three independent subprojects:
- `backend/` — FastAPI REST API (Python 3.12)
- `frontend/` — Flutter mobile/web app
- `embedded/` — ESP32 firmware (PlatformIO/Arduino)

## Backend

### Running

```bash
cd backend
cp .env.example .env          # first time only
docker-compose up -d          # starts api, db (TimescaleDB), redis, mqtt (EMQX), otel-collector, prometheus
docker-compose exec api alembic upgrade head   # apply migrations
```

API docs: http://localhost:8000/docs  
Health: http://localhost:8000/api/v1/health

### Common commands

```bash
# Migrations
docker-compose run app alembic revision --autogenerate -m "description"
docker-compose run app alembic upgrade head
docker-compose run app alembic downgrade -1

# Tests (requires a running PostgreSQL on localhost:5432 with db test_greenhouse)
docker-compose run app pytest
docker-compose run app pytest app/tests/test_alert_system.py   # single file

# Linting
docker-compose run app ruff check .
docker-compose run app mypy app/
```

### Architecture

**Layer order:** `api/v1/` → `services/` → `repositories/` → `domain/` (SQLAlchemy models) → `infrastructure/`

- `app/core/config.py` — Pydantic settings, reads from `.env`. Required env vars: `SECRET_KEY`, `POSTGRES_*`, `REDIS_URL`, `MQTT_HOST`.
- `app/infrastructure/` — Database session factory, Redis client, MQTT client.
- `app/domain/` — SQLAlchemy ORM models. `BaseEntity` (from `domain/base.py`) provides `id`, `created_at`, `updated_at`. `Greenhouse` owns `Device`s via cascade. `Telemetry` is a TimescaleDB hypertable partitioned by `(device_id, timestamp)`. `Prediction` stores per-greenhouse yield-prediction history (one row per worker run).
- `app/repositories/` — Async SQLAlchemy queries, one per domain model.
- `app/services/` — Business logic. `auth.py` handles JWT (access + refresh tokens). `discovery.py` handles device auto-registration from MQTT.
- `app/api/v1/` — FastAPI routers. Dependency injection wired in `api/deps.py` (DB session, current user).
- `app/workers/` — Three background tasks started at lifespan:
  - `mqtt_worker` — ingests telemetry from MQTT.
  - `ml_prediction_worker` — every 120s, for every greenhouse, aggregates that greenhouse's telemetry over the last 120s window (temperature avg/min/max, humidity avg, CO2 avg, light avg), runs the yield model, and persists a `Prediction` row. History is exposed via `GET /api/v1/ml/predictions/greenhouse/{greenhouse_id}` (owner-only). A prediction is only produced when a trained model exists, the greenhouse `extra_metadata` has `crop_type`/`variety`/`planting_date`/`harvest_date`, and telemetry exists in the window.
  - `ml_training_worker` — on startup trains a model **only if** none exists and `data/raw/greenhouse_crop_yields.csv` is present (no model writes where `ML_MODEL_PATH`/`InferenceService` reads); `POST /api/v1/ml/train` (admin) forces a retrain.

**MQTT topic format:** `greenhouse/<greenhouse_id>/device/<device_id>/telemetry` (telemetry, device→backend) and `greenhouse/<greenhouse_id>/device/<device_id>/commands` (commands, backend→device). The backend also broadcasts a retained `greenhouse/mapping` payload that lets a device resolve its MAC address to a `device_id`.

**Observability:** OpenTelemetry traces exported to `otel-collector:4317`. Prometheus metrics on port 8008.

## Frontend

### Running

```bash
cd frontend
flutter pub get
flutter run                   # Android emulator uses 10.0.2.2 to reach host localhost
```

### Common commands

```bash
flutter test                  # all tests
flutter test test/widget_test.dart   # single test
flutter analyze               # static analysis
flutter pub run build_runner build --delete-conflicting-outputs   # regenerate .g.dart files
```

### Architecture

Feature-based clean architecture under `lib/features/<feature>/`:
- `data/` — repository implementations, DTOs
- `domain/` — repository interfaces, entity classes, `.g.dart` generated by `json_annotation`
- `presentation/` — Riverpod controllers/state + pages/widgets

`lib/core/` contains shared infrastructure:
- `network/` — Dio client (`dio_provider.dart`), `api_endpoints.dart`
- `storage/` — `shared_preferences` (non-sensitive) and `flutter_secure_storage` (JWT tokens)
- `theme/` — neon-dark design system
- `navigation/` — app router

**State management:** Riverpod 2 (`flutter_riverpod` + `riverpod_annotation`). Controllers live in `presentation/` alongside the pages they serve.

**MQTT:** `mqtt_client` package handles real-time telemetry updates on the dashboard.

**Push notifications:** Firebase Messaging (`firebase_core`, `firebase_messaging`) + `flutter_local_notifications`. FCM tokens stored server-side via `POST /api/v1/notifications/fcm-token`.

## Embedded (ESP32)

### Building & testing

```bash
cd embedded
pio run                          # build for esp32dev
pio test -e native               # run desktop/unit tests (no hardware required)
pio test -e esp32dev             # run tests on connected device
pio device monitor               # serial monitor at 115200 baud
```

### Architecture

All code is under the `Greenhouse` namespace. `src/main.cpp` wires global singletons; all components are in `lib/`:

- `ConfigManager` — NVS-backed persistent config (WiFi creds, MQTT config, device identity)
- `WiFiProvider` / `MQTTProvider` — connectivity singletons
- `SystemContext` — holds shared runtime state
- `Sensor` / `DHTSensorImpl` / `LDRSensorImpl` / `MQ135SensorImpl` — sensor abstraction
- `DiscoveryService` — publishes device identity so the backend can auto-register it

Sensors: DHT22 (temperature/humidity), LDR (light), MQ135 (CO2).

`test/test_desktop_*` run natively via the `native` PlatformIO env (no Arduino dependencies). `test/test_embedded/` runs on hardware.
